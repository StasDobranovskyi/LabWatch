# Базова лінія LabWatch для ЛР4

Це база порівняння, а не реалізація ЛР4. Плата STM32C031C6, 48 МГц; Ubuntu 24.04, Docker, STM32 HAL, Wokwi; UART 115200 8N1. Сценарії S1–S3 виконано на source fingerprint `d7c3f569f1d1dfb638999a4578bc940a164f577837d2776d9796671d594cf9fa`, ELF SHA-256 `fbb10f8e971e68c7f920f759c0a21c769ec9440fff2cd9f60147864f338789f2`, Git base під час вимірювання `9d174589d4ec`. Повний source fingerprint охоплює вміст джерел, linker script, firmware Makefile та diagram за `tools/stamp.py`. Новий Git HEAD змінює поле base у банері і може змінити ELF: не називати новий ELF виміряним без повторної перевірки.

`board_micros()` використовує HAL SysTick ×1000, роздільність 1 мс; старе повідомлення BOOT про TIM3 1 MHz помилкове. UART-маркери у VCD додають затримку черги та серіалізації. `load_estimate_permille` охоплює вимірювані ділянки задач, а не повну утилізацію CPU. Одним супервізорним стеком користуються цикл та IRQ; окремих стеків RTOS немає.

Прив'язка для ЛР4: один і той самий набір каналів/стимулів та формати UART STAT/HEALTH, оригінальні UART/VCD, unit conversion і окремий контроль VCD. Контрольний S3 fixture виводить PA1, IMU marker PA6, journal marker PA7, dispatch PA10, ADC PA4, UART PA2/PA3 і LED PA5. Помічені S3 події обрамлені передачею JREC; це не доказ фізичного erase. Не змінювати одиниці або критерій вибірки між вимірюваннями.

Гіпотези для ЛР4, а не виміряні результати: (1) пріоритет задачі прийому зменшить пропущені слоти RX при тій самій UART-навантаженості; (2) пріоритет IMU зменшить додатний jitter S3 на 25% від спостережених 11 мс за відсутності flash stall; (3) контрольована backpressure для черги зменшить queue_lost за тим самим burst, із вимірюванням ціни для latency та RAM. RTOS не відновлює втрачений sensor baseline, не збільшує flash і не робить power cut атомарним. Перевірити сумарні витрати task stacks, scheduler та контекстних перемикань; переваги super loop (один стек, явний порядок, немає kernel context switch) збережені як структурні факти, не як виміряний виграш продуктивності.

## Додаткове випробування 01.11.2026

Плани host 2/10/40 status/s дали у шестисекундних вікнах VCD 2,00/9,17/23,67 status/s. На HEALTH 82017 мс RX/TX overflow ще 0, на 84015 мс tx_loss=4; після одноразового burst 100 команд є два rx_overflow. Ці лічильники не є кількістю байтів. Фінальний command RX→dispatch STAT n=337, max=132000 мкс; це не затримка повної відповіді. IMU STAT за весь короткий запуск: n=5126, max=21000 мкс, 2 deadline misses.

Нормальний startup один раз: SAMPLE має firmware time_us=28000, UART TX починається на VCD 74,987 мс (включає чергу); startup not-ready не випробувано. Для відтворення конфігурацію та похідний collector збережено в `fault-boundary-d7-ready/` і `tools/collect_fault_boundary_d7.py`; точна виміряна збірка й raw залишаються в локальному Work. Нова збірка після зміни HEAD може мати інший ELF. Не вважати режим фізичним power cut або SDA short.
