# План ЛР1 та ЛР2

## ЛР1

Використано наявний репозиторій власника й незмінений шаблон Nucleo-C031C6. Підготовлено README, словник, PRD, дослідження моделей, сценарії та локальну історію. Дві чисті Docker-збірки перевірено на Mac, а виконання в Ubuntu VM і Wokwi ще потрібне.

1. Перевірити погодження теми й точний час припинення прийому 05.10.2026.
2. Передати архів у Ubuntu 24.04 за [інструкцією](vm-transfer.md). Перевірити ОС, Docker без sudo, виконати дві чисті збірки й зберегти окремі логи та SHA256.
3. Відкрити `firmware.ioc` у CubeMX для перегляду. Зняти справжні Pinout і Clock Configuration. Новий код для датчиків зараз не генерувати.
4. Відкрити цю копію у VS Code з доступною ліцензією Wokwi. Дочекатися стартового рядка, кількох `tick`, спостерігати LED. Зберегти скриншот і UART-лог лише після запуску.
5. Закрити прогалини datasheet/живлення з [таблиці компонентів](hardware-components.md).
6. Оформити PDF у `Lab01/Reports`, після перевірки додати копію в репозиторій. PR створює власник.

За уточненням від 23.09 ЛР1 завершується планом теми й реалізації, build/Docker/Git, ознайомленням із компонентами, UART і LED. PDF ЛР1, с. 6, окремо описує генерацію інтерфейсів і перевірку I²C readiness / осцилограм. Ці перевірки тут не виконано: сенсори ще не підключені, firmware, `.ioc` і схема не змінювались. Самої ініціалізації недостатньо для підтвердження роботи I²C.

## ЛР2

1. Отримати повні специфікації та звірити GPIO/ADC/I²C піни, напруги й струми. Реалізувати карту підключень у `.ioc` і `diagram.json`.
2. Написати окремі HAL-модулі PIR, MPU6050 та ADC/LDR. Перевірити фронт PIR, WHO_AM_I, знаки/одиниці IMU, напрям зміни ADC й помилки I²C. Arduino-приклади не переносити.
3. Замінити секундний блокуючий цикл базової демонстрації неблокуючим планувальником. Початкові цілі: IMU 50 Гц, PIR/ADC 20 Гц, heartbeat 1 Гц. Таймаути й тривалість журналювання не повинні блокувати інші джерела.
4. Додати UART-команди режимів та калібрування. Валідувати всю команду до зміни стану. Початковий режим після reset: очікування, без готового еталона.
5. Записати нормальний нерухомий і робочий цикл. Визначити еталон орієнтації, відхилення від фону й запас порога; перевірити шум біля межі. Еталон після обслуговування повторити.
6. Перевірити окремі драйвери, потім всі одночасно за [сценаріями](test-plan.md). Виміряти затримки в симуляції. Короткі імпульси не гарантуються за частоти 50 Гц без аналізу їхньої тривалості.
7. Зберегти результати кожного сценарію: вхідні значення, пороги/версію калібрування, UART-запис, час реакції, скриншот. Перенести результати з VM через окремий inbox та порівняння.

Поки що не визначені модель приладу, робочий профіль вібрації, пороги удару/орієнтації/світла і прийнятний запас помилок. Запропоновані числа PRD потрібні для початку тестів, а не як уже виміряні характеристики.
